# Security

This document describes what is implemented, how it was verified, and where the limits are.
It is updated as each phase lands.

## Reporting a vulnerability
Open a private security advisory on the GitHub repository. Do not file public issues for vulnerabilities.

## Implemented (Phase 1)

| Area | Control | Verified by |
|---|---|---|
| Passwords | Argon2id, per-password salt, rehash on parameter change. Minimum 10 characters. | `tests/test_auth.py::test_password_is_hashed_and_token_is_hashed` |
| Sessions | 256-bit random token in an `HttpOnly`, `SameSite=Lax` cookie (`Secure` in production). Only a SHA-256 hash is stored, so a database leak does not yield usable sessions. 7-day sliding expiry. Logout deletes the server-side session. | `test_logout_invalidates_server_side`, `scripts/e2e_web.py` |
| User enumeration | Wrong password and unknown email return identical responses; a dummy hash is verified so timing is similar. | `test_wrong_password_and_unknown_user_are_indistinguishable` |
| Brute force | Login limited per IP (20 / 15 min) and per email (8 / 15 min). Registration limited per IP. | `test_login_rate_limited` |
| CSRF | State-changing requests require `X-Requested-With: QuantaLens`, which cross-site forms cannot set. Combined with `SameSite=Lax`. | `test_csrf_header_required_for_state_changes` |
| Authorisation | Every data query is scoped by `user_id`. | `tests/test_overview.py::test_overview_counts_only_own_data` |
| Secrets | Read from environment only. `.env*` is git-ignored. `ANALYTICS_DATABASE_URL` and the LLM key are never sent to the browser. | Manual review; `.gitignore` |
| SQL role | Generated SQL will run as `quantalens_readonly`: SELECT on schema `qdata` only, read-only transactions, 15 s statement timeout, 10 connections. Cannot read `users` or `auth_sessions`. | `scripts/verify_readonly_role.py` (11 checks against Neon) |
| Headers | `X-Content-Type-Options`, `X-Frame-Options: DENY`, `Referrer-Policy`, `Permissions-Policy`. API docs disabled in production. | Config review |
| Errors | Unhandled exceptions return a generic 500. Only the exception type is logged, never its message. | Config review |

## Implemented (Phase 2)

| Area | Control | Verified by |
|---|---|---|
| Upload validation | Extension checked, then content: archives, PDFs, images, executables and NUL bytes are rejected regardless of filename. Encoding and delimiter detected. Column and row caps. Filenames reduced to a safe basename. | `tests/test_parsing_and_reader.py`, `tests/test_datasets_api.py` |
| Upload size | Enforced while streaming (ASGI middleware), including chunked bodies without Content-Length, plus a per-user storage allowance and dataset count. | `TestSizeLimit` |
| Original data | Stored as text and never modified. Cleaning writes a separate table. | `test_cleaning_workflow_never_touches_the_original` (digest before and after, on Neon) |
| Query building | Table and column identifiers are quoted with `sql.Identifier` and checked against the stored schema. Search terms and filter values are bound parameters. `%` and `_` are escaped. | `test_sql_injection_attempts_are_inert` |
| Isolation | Unknown and foreign dataset ids both return 404, so ids cannot be probed. | `TestOwnership`, `test_user_isolation` |
| Error disclosure | Processing failures store a fixed message. Internal error text is never returned or logged. | `test_processing_failure_is_reported_and_cleaned_up` |
| Deletion | Drops the original and cleaned tables, then the metadata. A request during deletion gets 404, not a stack trace. | `test_rename_and_delete_remove_everything` |

## Implemented (Phase 3: AI analyst)

### SQL generated by the model
The analytics database role can read **every user's** tables in schema `qdata`; it is least-privilege (no writes, no application tables) but not per-user.
**The SQL guard is therefore the isolation boundary between users.** `app/analysis/sql_guard.py` parses the query and enforces:

| Rule | Detail |
|---|---|
| One statement, SELECT only | Writes, DDL, `COPY`, `SET`, transactions, `INTO`, `FOR UPDATE`, data-modifying CTEs are rejected. |
| One relation | Only the virtual table `data` (rewritten to the dataset's own table) and CTEs defined in the same query. Other tables, other schemas, `pg_catalog`, `information_schema` are rejected. |
| Function allowlist | Unknown functions are rejected. This blocks `query_to_xml()` (runs arbitrary SQL text), `pg_read_file`, `pg_sleep`, `dblink`, `set_config`, `lo_*`, `version()`, `current_user`. |
| No `reg*` casts, no table-valued functions, no system columns | |
| Row and time limits | Rows capped at 1,000 (1,001 fetched to detect truncation). 10 s statement timeout, read-only transaction. |
| Executed text is regenerated from the syntax tree | Comments and parser tricks never reach the database. The UI shows both what the model wrote and the exact statement that ran. |

Verified by 87 unit tests and by integration tests against Neon, including a hostile query naming another user's table and the database role refusing writes with the guard bypassed.

### Python generated by the model
**This is a restricted runner, not a hardened sandbox.** Layers, in order:
1. AST allowlist: only pandas, numpy, scipy, scikit-learn and a few standard modules; no dunder or private attributes; no `getattr`, `eval`, `open`, `type`; no `str.format` (a known escape route); file readers and writers blocked by name; code that embeds many numeric literals is rejected so results cannot be retyped.
2. In the child process: restricted builtins and a guarded `__import__`.
3. A Python audit hook installed before the code runs, which blocks sockets, subprocess creation, file writes, reads outside the Python installation, and loading libraries from elsewhere.
4. A separate process with an empty environment (no database URLs, no API keys), a 25 s wall-clock limit, a temporary working directory that is deleted afterwards, and at most two concurrent runs.
5. On Linux: memory (1 GB), CPU time and file-size limits through `resource`.

Verified by 98 tests, including tests that **bypass the static check** to show the later layers hold on their own (file write, file read, network, subprocess and import attempts).

What it does **not** protect against:
- A bug in CPython or a C extension (numpy, pandas, scipy) that a crafted input could exploit. Python audit hooks are not a security boundary against native-code exploits.
- Resource exhaustion on hosts without `resource` limits. **The memory limit has not been tested on this project's Windows development machine** (the test is skipped there). It is untested until run on Linux.
- A malicious tenant on a shared host. For a public multi-tenant deployment, run the engine in a container with no network, a read-only filesystem and a non-root user, or move execution to a dedicated sandbox service.

### AI-specific controls
- **Prompt injection:** dataset values, column names and file names are untrusted. They are flattened (control characters removed, length capped), presented as data with an explicit warning, and the system prompt is never modified by them. The model's only abilities are the tools; every tool is guarded independently of what the model "decides".
- **No credentials reach the model.** Database URLs, keys and secrets are never placed in prompts, tool outputs or logs.
- **No hidden reasoning is stored or shown.** The UI shows the plan, the tool calls and their real results.
- **Numbers are checked, not trusted.** Validation recomputes figures by a different route (separate SQL built by the application from whitelisted columns and bound values; arithmetic on stored cells). A scan lists any figure in the written answer that matches no stored result. Neither can catch every error: they cover the checks the model requests and the figures it states, and a wrong *interpretation* of correct numbers can still occur. Status labels (`verified`, `partially verified`, `unverified`, `failed`, `not validated`) are computed by the server, never written by the model.
- **Rate limits:** 30 questions per hour per user, one running analysis per conversation, 5 generated sample datasets per hour.

### Privacy: what is sent to the AI provider
When you ask a question, the following leave this system for the AI provider's API: your question, column names, up to five example values per column (40 characters each), and the first 25 rows of each query result the model requests. **On Google's free Gemini API tier, Google's published terms allow prompts to be used to improve its products. Do not use the free-tier key with confidential or personal data.** Use a paid key (with its data-use terms reviewed) or a self-hosted model for sensitive datasets. The provider is configurable (`AI_BASE_URL`).

## Known limits

- **Spreadsheet formulas** (`=SUM(...)`) in uploaded cells are stored as plain text. Exports in Phase 5 must neutralise them.
- **Uploaded data is held in memory** while it is parsed and profiled. The 50 MB cap bounds this, but it is the main memory cost on a free host.
- **No malware scanning** of uploads. Files are parsed as text only and never executed.

- **Rate limiting is in memory** and per process. It resets on restart and is not shared across instances.
  Adequate for a single free-tier instance; a scaled deployment needs a shared store.
- **Client IP** for rate limiting is taken from `X-Forwarded-For`. A client that reaches the engine directly could
  spoof it, so the per-email limit exists as a second control.
- **Registration reveals whether an email is registered** (409). This is a usability trade-off and is rate limited.
- **No email verification or password reset yet.**
- **The Python runner is not yet built.** When it is, it will be a restricted subprocess, not a hardened
  sandbox. This document will describe exactly what it does and does not protect against.
