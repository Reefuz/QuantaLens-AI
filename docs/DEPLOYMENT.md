# Deployment

QuantaLens runs as two services plus a database:

| Part | Host | Source |
| --- | --- | --- |
| Frontend (Next.js) | Vercel | `apps/web` |
| Analytics engine (FastAPI) | Render, Docker, free plan | `apps/engine`, `render.yaml` |
| Database | Neon Postgres | one project, schema `public` for the app and `qdata` for datasets |

The browser only talks to the Vercel origin. `next.config.ts` rewrites `/api/*` to the engine
(`PYTHON_ANALYTICS_API_URL`), so session cookies are first-party and CORS is not needed for normal use.

## 1. Database (Neon)

1. Use a dedicated Neon project or branch for production if you can.
2. Rotate the password for any credential that has been pasted into a chat or log.
3. Run migrations. The engine container does this on every start (`alembic upgrade head`).
4. Create the read-only role used for generated SQL. Run once from `apps/engine` with `DATABASE_URL` pointing at production:

   ```powershell
   python -m scripts.provision_readonly_role
   ```

   It prints the `ANALYTICS_DATABASE_URL` for the new role. Use `--rotate` to change its password later.
   `python -m scripts.verify_readonly_role` runs the 11 checks that prove the role cannot write.

## 2. Engine (Render)

1. In Render choose **New > Blueprint**, select this repository. It reads `render.yaml`.
2. Fill the values marked `sync: false`:

   | Variable | Value |
   | --- | --- |
   | `DATABASE_URL` | Neon application role connection string |
   | `ANALYTICS_DATABASE_URL` | Connection string of `quantalens_readonly` (must differ from the above) |
   | `AI_PROVIDER_API_KEY` | Google AI Studio key |
   | `ALLOWED_ORIGINS` | The Vercel URL, for example `https://quantalens-ai.vercel.app` (https only, no wildcard) |

   `AUTH_SECRET` is generated by Render. With `APP_ENV=production` the engine refuses to start if a required value is missing or weak.
3. Check `https://<service>.onrender.com/health`. It returns `{"status":"ok","ai_configured":true}`.

The free plan sleeps after inactivity, so the first request after a pause is slow. The free plan has 512 MB of RAM, which is why
`PYTHON_MEMORY_MB=400` and `PYTHON_MAX_CONCURRENT=1` are set.

## 3. Frontend (Vercel)

Project root directory: `apps/web`. Environment variables:

| Variable | Value |
| --- | --- |
| `PYTHON_ANALYTICS_API_URL` | The Render URL, no trailing slash. Server side only. |
| `NEXT_PUBLIC_APP_URL` | The Vercel production URL |
| `NEXT_PUBLIC_UPLOAD_URL` | Optional. The Render URL. Only set it if large uploads fail through the proxy (below). |

Deploy with `vercel --prod` from `apps/web`, or connect the GitHub repository.

### Upload size

Vercel documents a 4.5 MB request body limit for Functions. It does not document the limit for rewrites to external
origins. Run the smoke test to measure it. If the 8 MB upload fails with 413, set `NEXT_PUBLIC_UPLOAD_URL`.
The browser then asks `POST /api/datasets/upload-token` for a 5-minute single-use token and sends the file straight to the
engine as `Authorization: Bearer`. This needs `ALLOWED_ORIGINS` to contain the Vercel URL.

## 4. Smoke test

```powershell
cd apps/engine
.\.venv\Scripts\python -m scripts.smoke_prod https://<vercel-url> --engine https://<service>.onrender.com
```

It registers a throwaway account, uploads a small and an 8 MB CSV, checks cookies and the upload token, then deletes the account.
It exits non-zero on any failure. Run it after every production deploy.

## 5. CI

`.github/workflows/ci.yml` installs the engine from `requirements.txt` with `constraints.txt` on Linux, runs the unit tests
(including the Linux-only memory-limit test), then lints and builds the web app. Integration tests need a real database and
run only with `RUN_INTEGRATION=1`.

## Not covered

- The Docker image has not been built locally (Docker is not installed on the development machine). Render builds it on first deploy.
- The Python sandbox is defence in depth, not a hardened sandbox. See `SECURITY.md`.
